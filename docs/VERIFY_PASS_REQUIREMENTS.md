# Vol 11 `[?]` verification pass against the better scan — requirements

Self-contained brief for a fresh Claude Code session. Read it fully, then also read `CLAUDE.md` (project conventions) and the last 20 lines of `docs/PASS_LOG.md`.

## 1. Task in one paragraph

The repo holds an English translation and a Kannada transcription of Vol 11 of a 1949 Kannada commentary on the Ṛgveda (Maṇḍala 1, Sūktas 137–157). Both files were first made from a poor scan and contain thousands of `[?]` marks (doubtful readings) and some silent misreadings. The user has supplied a **better 600 dpi scan** covering PDF pages 1–140 of the volume. The task is to go page by page, re-read the better scan, and (a) resolve each `[?]` where the print is now legible, (b) correct any unflagged misreading found, in **both** files, (c) leave a `[?]` where a glyph is still doubtful, and (d) log each batch.

## 4. Setup (once)

1. The user has two PDFs: `11_Rigveda_Samhitha_Volume_11-1-70.pdf` and `11_Rigveda_Samhitha_Volume_11-71-140.pdf`. Ask where they are; do **not** commit them.
2. `sh publish/tools/verify11/merge_scans.sh <first.pdf> <second.pdf>` makes `$VERIFY_WORK/new.pdf` (default `~/verify_work/new.pdf`) with 140 pages, so PDF page N of the scan = PDF page N of the volume. Check `pdfinfo` says 140 pages and that page 71 is printed p. 53.
3. Needs poppler (`pdftoppm`, `pdfunite`), Python 3 with Pillow. On macOS: `brew install poppler`.
4. If two sessions are working at once, use **separate branches and separate page ranges** (e.g. this one 73–106, the other 107–140), `PASS_LOG_FILE=docs/PASS_LOG_<tag>.md` for logging, and merge by hand; both md files are single large files, but edits in different page regions merge cleanly. Never rewrite history.

## 5. Per-page workflow (this is what worked)

For each PDF page N:
1. `python3 publish/tools/verify11/ctx.py N` — lists every `[?]` with context, English and Kannada separately.
2. `python3 publish/tools/verify11/strips.py N 3` — makes `$VERIFY_WORK/pN_1.png … pN_3.png`. View the three strips (the viewer shows them about 1.05–1.09× smaller than the original pixels). Read the page once, comparing with what the files say.
3. For every doubtful glyph — above all **numerals** in references — make a zoom: `python3 publish/tools/verify11/tiles.py N STRIP "x0,y0,x1,y1;…"` (box coordinates in original strip pixels = displayed coordinates × original_width/displayed_width). View `$VERIFY_WORK/tiles.png`. Misaligned boxes are the usual failure; check the first tile before reading more.
4. Edit both files with `python3` using `fx.py`: `en(N,[(old,new)])`, `kn(N,[(old,new)])`, `sk(N,[(old_dev,new_dev)])` (Sanskrit: patches Devanagari, regenerates IAST, patches the Kannada-script copy). These refuse silently-ambiguous edits (they print `!!` unless the old text occurs once on that page). For repeated patterns use ordered regex replacement. Whole Sanskrit blocks that were badly misread are best rewritten from the image and regenerated (`deva_to_iast`, `deva2kn`).
5. Re-run `ctx.py N`; the remaining `[?]` should be only the deliberately kept ones.
6. Log: `python3 publish/tools/pass_log.py N N "what changed; what stays doubtful"`.
7. Every 2–4 pages: `git add -A <the two md files> docs; git commit; git push` (see §7). Do not wait to commit a long run.

Tips learned: view each page once; zoom only crops that cannot be read; keep numerals as printed even if they differ from the standard number; the Kannada font draws ಮ like "ಮು" and ṅ (ಙ) like ಜ; page strips at 260 dpi are enough for prose, tiles at 520 dpi for digits.

## 6. Accents (optional extra, English file only)

Convention in the print: underline = anudātta (U+0952 ॒), stroke above = svarita (U+0951 ॑), unmarked = udātta. Done for Saṃhitā lines up to Sūkta 139 Ṛk 4 (printed p. 55). For each new Ṛk Saṃhitā block: `python3 publish/tools/verify11/vcrop.py N y0 y1 x0 x1 tag` (fractions of the page; try 0.60 0.88 0.19 0.90 and adjust) gives `tagL.png` and `tagR.png` at 400 dpi; view both halves and any ambiguous mark up close. Then `from acc import apply; apply(["accented line 1", …])` — each accented line must equal the existing Devanagari line once the marks are removed; the IAST line is regenerated. Place a mark on the syllable it is printed over/under; conjunct marks go on the last consonant's syllable; where a mark is genuinely ambiguous, choose the nearer syllable and mention it in the log. Do not add accents to the Pada lines or the Kannada file. While doing this, **read the verse itself from the print** — earlier transcriptions had stray or missing words (e.g. a duplicated *ajāśva*).

## 7. Rules (from `CLAUDE.md`, restated)

- Never complete a garbled word from memory; keep `[?]` where a reading is doubtful; bracket nothing else.
- Record numerals as **printed**; if different from the standard number, say so ("as printed"). Many sūtra numbers are simply not printed — give none; never supply from memory.
- Sanskrit always in three layers (Devanagari, IAST, English gist/translation). Bhāṣya stays in Sanskrit with a one-line gist only.
- Take the Kannada source at face value; no outside cross-checking except standard reference material.
- Each md file ends with exactly one `**Progress note:**` block; do not duplicate it. Do not edit other volumes' files.
- Commits end with: `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>` and `Claude-Session: <your session url>`. Push to the branch you were given and to `main` only if the user says so; no pull requests unless asked. No model identifiers in repo files.
- Ask the user before large or irreversible steps.

## 8. Acceptance criteria

- After each batch: `ctx.py` for those pages shows only intentional `[?]`; both files changed consistently (English/Kannada); a log line is appended; commit pushed.
- No new `[?]` removed without looking at the image for that item. No numeral supplied from memory.
- At the end of the 140 pages: rebuild the volume's DOCX/PDF only if the user asks; update the two progress notes to say "better-scan pass done through PDF 140; remaining `[?]` are on pages 141+ or are doubtful numerals"; report counts before/after (use `git show <first-commit-of-pass>^:<file>` vs current).

## 9. Reporting
