# Using a user-supplied numeral file (xlsx) — lessons from Vol 7 (Nov 4 2026)

Read this before any numeral pass on a new volume. Scripts are in this folder; per-step results for Vol 7 are in `vol7/numerals/README.md`.

## The file
- Columns: Page | Line | Kannada digits | English digits | Raw line context (noisy Kannada OCR, "column E"). It lists **only references with separators** (4-5-2, 4.5.6); plain numbers (124, 34) are never in it. **Ask which file version is current and what the page offset is (Vol 7 newest file: file page = PDF page).** Keep every version in `volN/numerals/`.
- **The user treats the file as always correct** and said every row flagged DIFFERENT had the right value. It is still machine OCR: it sometimes loses/shifts separators (`7-4-79` → `7-479`, `79-4` for 7-9-4 — the user confirmed such values are right), reads digits as 0 (`2-00`, `0-08`) or merges rows. Never "fix" the file from memory; ask the user when a pairing looks like two different references.

## Core rule (user, Nov 4 2026): match EVERY numeral, with context and approximate line position — never only the `[?]` ones
- **Scope = all md numerals**, flagged or not. Unflagged numerals carry errors too (Vol 7: 495 DIFFERENT rows, most never marked `[?]`). Going only through `[?]` numerals misses them, and a `[?]` on a value that already equals the file stays forever.
- **Direction = go through the file line by line** (each row has page and line number) and find the md numeral it corresponds to, instead of starting from the md.
- **Every pairing must use three signals together, not digits alone:**
  1. **Context** — column E (Kannada, transliterated and folded) against the md text just before/after the numeral (Devanagari→IAST folded, English words). Also the reference-type hint (ನಿ. = Ni., ಪಾ. = Pā., ಋ./ಖು. = Ṛ., ಕಾ. = Kā.…). Context scores are noisy (0.3–1.0); use as a tie-breaker and as the sorting key for review (≥ 0.8 is almost always the right pairing).
  2. **Approximate line position** — the file's line number is not the md line, but the **order** is preserved: on a page, file rows sorted by line and md numerals in reading order must align monotonically (rows may be skipped, never reordered). Use the line number's rank on the page as a position estimate (rank/total on the file side vs rank/total of md numerals), and let the alignment (dynamic programming) enforce the order. **Implemented in `numeral_align_all.py` (score = 0.55 digits + 0.30 context + 0.15 position, position = rank on the page, neighbour pages offset by ±1).**
  3. **Digits** — edit-distance similarity, with a penalty for a different part count; never let digits alone decide when two candidates remain.
- Statuses to report for every file row: SAME / SAME-but-md-has-[?] / DIFFERENT / NOT FOUND, each with page, file line, md line, scores. Nothing is changed in this step.
- The page-pool "nearest unused entry" method (`numeral_nearest.py`, `numeral_pageset.py`) ignores order and context; it is a fallback for doubtful numerals only, never the first pass.

## Mistakes to avoid (all happened in Vol 7)
1. **Only scanning Devanagari lines.** The md carries one reference on several lines: the Devanagari line, its italic IAST twin, English renderings. A citation can live **only on an italic `*…*` line** (Vol 7 p. v: Ṛ. Saṃ. 10-130-4) or on a plain English line (p. ii: "pages 221–231"). Scan **every non-table, non-heading line**, then **dedupe**: the same value within ~8 lines counts once.
2. **Page headings.** Front-matter headings are roman ("### Page ii (PDF 8)"); a regex `Page\s+(\d+)` silently skips them. Use `(\w+)`.
3. **Matching by page only.** The page-set pooling (exact, then nearest unused entry) is good enough for exact matches and one-digit slips but pairs doubtful numerals with unrelated leftovers at distance ≥ 3. Use **reading order** (monotone alignment of the file rows with the md numerals; `numeral_align_all.py`) plus column E context and the digit score.
4. **Running a replacement before checking its output.** Review a sample of the preview for impossible results (extra parts, zero parts, a list `119, 124, 125` paired with `10-113-2`) before `--apply`. First nearest-entry run produced `6-4-24` → `6-4-24-4` and `Ni. 2-17` → `8-0`.
5. **Applying only to Devanagari lines** leaves the IAST twin and English renderings with the old value. Apply to the same old value within ±8 lines, or sweep afterwards (`numeral_sweep_english.py`).
6. **Pairing across `[?]` only.** Many errors are NOT flagged `[?]`. Compare **every** md numeral with the file, irrespective of `[?]`, and report SAME / SAME-but-[?] / DIFFERENT / NOT FOUND.

## Recommended order for a new volume
1. `numeral_align_all.py --md MD --num XLSX --out volN/numerals/VolN_file_vs_md.xlsx` (report only; check pages 8/10-style spot rows the user names).
2. `numeral_drop_q_same.py`: drop `[?]` where the md equals the aligned file row (user checked 291 of 291 correct in Vol 7).
3. `numeral_apply_different.py … --parts-ok` for DIFFERENT rows (drop `--parts-ok` first to see the part-count-changing ones separately; ask the user). It skips edit distance ≥ 4 and plain lists — those are mis-pairings; list them for the user.
4. Remaining `[?]` and NOT FOUND rows: workbook (`unused_entries_xlsx.py`, `numeral_verify_certain.py`) for the user to mark (`C` = md correct, or the digits).
5. Log every step as TSV in `volN/numerals/`, commit after each, note results in that folder's README, user answers recorded as "User confirmed".

## md-side pass (user, Nov 4 2026, Vol 8): "go line by line in the md and check every numeral irrespective of ?"
`numeral_align_all.py` writes a second sheet **"md numerals vs file"**: every md numeral (deduped) in reading order with the file row aligned to it (SAME / SAME-but-[?] / DIFFERENT / NOT IN FILE), scores, and for unaligned ones the three closest unmatched file rows on that page. Comma lists of references ("3-54-20, 5-69-3, 6-51-5") are split into one numeral per segment (a single token would never match). Vol 8 result: 4,796 md numerals → 2,177 SAME, 920 DIFFERENT, 1,699 no aligned file row (105 of them still `[?]`); Vol 7: 1,377 SAME, 144 DIFFERENT, 1,510 no row. Numerals with no aligned row are mostly references the file does not list (plain numbers, Kannada-prose numerals) or have digits so far from the file that nothing aligned — the "closest unmatched" column is the lead for those.

## Adjacent numerals are not rows in the file (user, Nov 4 2026)
Numerals next to each other (`೧೧೯, ೧೨೪, ೧೨೫`; a reference followed by `, ೫` / `ಮತ್ತು ೫` = same reference with the last part changed) are not listed as rows; they must be extracted from the **Kannada context column (the file has only columns A–E; the user said "column K" — it is column E, "Raw Line Context")** and translated. `numeral_align_all.py` does this: plain adjacent runs become one value ("119-124-125", matching the md's "119, 124, 125"), and `ref, N` / `ref ಮತ್ತು N` give `ref-with-last-part-N`; on the md side `ref, N` / `ref and N` is expanded the same way. Vol 8: +28 plain runs, +15 extensions; Vol 7: +32 runs. The effect on the alignment was small (the context column is a ~100-character fragment, so most neighbours are cut off): ask the user whether such numerals matter before spending more on this.

## Why file rows are "NOT FOUND in md" (Vol 8 analysis, Nov 4 2026; 508 rows → `vol8/numerals/Vol8_not_found_analysis.xlsx`)
Classified by rule, in priority order: **A running head / page number / folio 85** (file lines 1–2, "ಮಂ. 1 ಆ. 18 …", the md does not carry these as numerals); **B zero / leading-zero parts 35** (file OCR junk: 3-0, 3.09); **C value is in the md on the page but the aligner missed it 27** (alignment ties — rerun after the other fixes); **D digits present with different separators/grouping 72** (e.g. file `38-3` vs md `3-8, 3`; file `7-2` where the md has `7-2-…` split by OCR); **E one-digit variant on the page 10 / F two-digit variant 73** (md or file misreads: real leads, check on the page); **G English/OCR-junk context 20**; **H not in md 186** (74 Ṛgveda, 45 Pāṇini/Kāśikā/Uṇādi, 13 Nirukta references plus 54 unclear): the md omits them (grammar pages are "noted briefly" by convention; Special-Topics references) or reads them so differently that nothing near them exists on the page. So most "not found" rows are **not md errors**: ~120 are file-side junk (A, B, G), ~100 are alignment/format issues (C, D), ~83 are look-alike variants (E, F) and ~186 are references the md does not carry. Use the class column to decide what needs the user's eyes (E, F, then H-Ṛgveda).
Rule for the next volume: **strip file rows at lines 1–2 and those matching the running-head pattern before aligning**, and drop zero-part values, so the "NOT FOUND" list is not inflated by them.

## Lines with several references; incomplete md tokens (user, Nov 5 2026, Vol 9 row 757)
A file line can carry several references (`(ನಿ. ೩-೭) ಮತ್ತು (ನಿ. ೪-೨)` = two rows, same page and line) and the md line has the matching references **in the same order**, some of them *incomplete* ("Ni. 2-?? as read [?]", "Ni. 4-? as read [?]"). Digit-only tokens never see those. `numeral_align_all.py` now also reads incomplete md tokens (`4-?`, `2-??`) as value "4-?": the known prefix is compared with the file row's first parts (the file row must have more parts), and `numeral_apply_different.py` replaces the whole incomplete token (with its "as read" and "[?]") by the file's full value, only when the prefix is equal or differs by one same-length digit. Example md line 3990: `Ni. 3-2 and Ni. 4-? as read [?]` → `Ni. 3-7 and Ni. 4-2`. Effect on Vol 9: incomplete tokens 170 replaced; DIFFERENT 723 → 274 after the apply. **Vols 7 and 8 were aligned before this fix; re-run them** (their `4-?`-type tokens were not seen).
